# 算法社训练平台 AstrBot 通知插件

接收平台 `POST /club/notify`，调用 AstrBot 主动消息接口向指定群聊或私聊通知。
插件不会主动读取平台数据库，也不会在群聊泄露卡密。

## 安装与接收配置

1. 将本目录复制到 AstrBot 的 `data/plugins/astrbot_plugin_club_notify`；也可将本目录内容打包为 ZIP 后通过插件管理页面上传。使用 AstrBot 4.16+（小于 5），安装本目录 `requirements.txt` 的依赖。
2. 首次安装可以保持默认空配置：插件正常加载，通知 API 暂不监听，`/训练通知会话` 指令仍可使用。在插件配置中设置与平台团队通知配置相同的 `api_token`（至少 32 位），设置 `host`、`port`。多个团队使用不同密钥时，可在“团队专属密钥”列表逐项填写 `团队ID=密钥`；也可仅配置专属密钥、将顶部 api_token 留空。已配置专属密钥的团队只接受自身密钥，其他团队使用顶部 api_token。默认监听 `127.0.0.1:8099`。Docker 中如需跨容器访问，请监听 `0.0.0.0`，将端口只提供给平台/受控网络，跨公网使用 HTTPS 反向代理。
3. 展开“用户互动”，分别在“通知群 QQ 号”和“通知用户 QQ 号”列表中添加号码，每项一个号码，可添加多个。此组接收举报、商品使用和实物购买通知。
4. 展开“达标审查”，同样添加群号和用户 QQ 号。此组接收每周未达标提醒。两组接收人独立，可以只配置一组；新安装中未配置的类别不会发送，平台 API 请求返回 422 并保留待重试记录。号码重复填写时自动去重。
5. 仅有一个 OneBot v11（NapCat / Lagrange）连接时，会在发送时自动识别；多个连接时，请在“QQ 机器人连接 ID”填写 AstrBot 消息平台中的连接 ID。也可由管理员发送 `/训练通知会话`，取回复中第一个冒号之前的部分作为连接 ID。这不是机器人 QQ 号。QQ 官方机器人不能通过普通 QQ 号任意发私聊，请使用支持 QQ 号寻址的连接。
6. 保存配置后重载插件。机器人需已加入目标群或具有向目标用户主动发送消息的权限。两组可视化接收名单适用于平台所有团队，举报含举报人信息，请按需要选择接收人。

### 旧版配置兼容

升级保留旧版 `routes`，在界面中隐藏，无需重新填写。某类别填写了新的可视化号码列表后，该类别优先使用新名单（覆盖所有团队）；另一类别仍沿用原路由。只使用可视化配置的新安装不需要编辑 JSON。
若升级后希望彻底停用旧路由，可在 AstrBot 插件配置文件中把 `routes` 设为 `"{}"`，然后重载插件。

旧版 `routes` 使用完整 `unified_msg_origin`，会话中的平台实例标识必须与实际配置一致，不要直接照抄下面的 `qq`。

例如，团队 `1` 的举报发给管理员私聊，其他事件发给群：

```json
{
  "1": {
    "submission_report": ["qq:FriendMessage:123456"],
    "*": ["qq:GroupMessage:987654"]
  }
}
```

事件：`submission_report` 举报、`item_used` 商品使用、`physical_purchase` 实物购买、`weekly_unqualified` 周统计。
团队键 `*` 表示未配置团队的回退；事件键 `*` 表示该团队未配置事件的回退。
具体团队配置会完全替代全局团队配置。数组可以包含多个群和用户；通知目标只从插件本地配置读取。
请注意举报含举报人信息，建议将举报单独发送至管理会话。

## 平台配置

在训练平台 `.env` 添加（示例密钥不能用于生产）：

```dotenv
ASTRBOT_NOTIFY_URL=https://your-bot.example/club/notify
```

平台“管理工作台 → 团队配置 → 通知配置”中开启总开关，填写或随机生成并保存密钥，将相同密钥填写到插件。四类通知可独立启停，达标审核可选择每周几及具体时间。总开关默认关闭，密钥加密保存，关闭期间的事件不会回补；关闭通知会取消尚未送达的同类事件。环境变量 `ASTRBOT_NOTIFY_TOKEN` 不再作为团队发送密钥。

通知 API 地址留空也会停止发送。更新平台代码后执行迁移（包含 `0042_team_notification_settings`），并重建/重启 web、worker、beat。
Docker Compose 项目可运行：

```bash
docker compose up -d --build web worker beat
```

平台通知行为：

| 触发 | 发送内容 |
| --- | --- |
| 首次成功提交举报 | 举报人、被举报人、提交编号、版本 |
| 消耗品使用、卡密核销、补签券使用成功 | 成员、商品、使用记录/补签日期；不含卡密 |
| 实物购买成功 | 成员、商品、数量、订单编号，提醒发货 |
| 团队配置的每周审核时间（默认周日 21:00，北京时间） | “本周尚未达标的同学有：”及名单、积分、有效提交数 |

后台每 60 秒处理一次，通常一分钟内推送。周统计在团队配置的审核时间后首次执行时生成快照，在配置的审核日午夜前可补跑；若整个窗口停机则不会补发上周提醒。采用活动且未归档学期当前周的已批准积分，以及有效且通过截图审核的提交数，沿用平台 `submission_stats` 口径。纳入团队启用成员和启用账号，排除系统管理员；没有提交的成员按 0 计算。
判定固定为 `积分 < 6 OR 有效提交 < 4`，不跟随学期其他达标设置。没有未达标成员时明确发送全员达标。每个学期每个训练周只生成一条快照，修改审核时间也不会重复生成本周快照；重试沿用原名单。

平台把事件与业务记录写入同一数据库事务，回滚时不发送，重复业务请求不新增事件。
网络或消息适配器失败时持续退避重试（最长间隔一小时）；已送达记录不再发送。平台保存出站队列，插件在 AstrBot `data/plugin_data` 下保存每个事件、会话、消息分段的送达记录，重载/重启后仍去重；失败会话不影响已送达会话的记录。
无法在消息平台与本地数据库间实现原子提交：如果消息已发送后立即崩溃、尚未记录成功，重试可能重复。不要删除插件送达数据库，否则旧请求可能再次发送。大量长名单/多目标需要多个重试周期才能完成。

## API 协议

请求头：`Authorization: Bearer <api_token>`，`Content-Type: application/json`。

```json
{
  "event_id": "343754cd-5c82-4446-8e1b-21d7532fc085",
  "event_type": "weekly_unqualified",
  "team_id": 1,
  "team_name": "算法社",
  "text": "本周尚未达标的同学有：\n小明（积分 5，有效提交 3）",
  "data": {"min_score": 6, "min_submissions": 4}
}
```

成功及重复请求均返回 `200 {"ok": true, "event_id": "..."}`；未认证 401、参数错误 400、相同事件 ID 不同内容 409、未配置接收会话 422、发送失败 503。失败后使用相同 ID 和内容重试。API 最大请求 1 MiB，文本最多 200000 字符，自动按 1500 字符分段。
`text` 为平台生成的通知正文；插件不接收调用方指定的目标会话。

排障：先检查插件是否加载、监听地址及端口可达、两端 token 是否一致、团队 ID 和会话配置是否准确、平台 worker/beat 是否运行。平台 `AstrBotNotification` 中的 `attempts`、`last_error`、`delivered_at` 可用于检查积压；错误信息不保存密钥或远端响应正文。
